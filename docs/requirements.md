# 产品需求梳理（Curtain）

Platform decision (2026-11-06): support Apple Silicon (arm64) only, on macOS 15 or later.

Distribution decision (2026-11-06): distribute `Curtain-arm64.dmg` for drag-to-Applications installation and a signed `Curtain.zip` for in-app updates, without App Store submission, Developer ID distribution signing, or Apple notarization. Users may need to approve the first launch in macOS Privacy & Security. In-app updates authenticate ZIP archives with an independently maintained Ed25519 key and use GitHub Releases at `iwaller/curtain`. Existing local Apple Development signing remains available; ad-hoc signing does not require a signing certificate. See the [distribution contract](subsystems/app-maintenance.md#distribution).

agent 不限于 Codex，适用于基于截图和模拟输入的 Computer Use 类 agent。

日期：2026-11-04。状态：需求整理，用户已确认第一版取舍（见文末“已决定”）；未实现，技术可行性按条目标注。

## 使用场景

下班离开工位时，从菜单栏触发隐私屏：实体屏幕看不到桌面，路过的人无法操作电脑；Codex Computer Use 仍在当前登录会话中继续工作；用户可能通过 UU 远程查看或操作。第二天上班，在隐私屏上用电脑登录密码或 Touch ID 解锁，回到正常桌面。

## 功能需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F1 | 菜单栏常驻 | 只显示菜单栏图标，不出现在 Dock；菜单含“开启隐私屏”“退出”等 |
| F2 | 开启隐私屏 | 所有显示器立即变黑，切换 Space、进入或退出原生全屏、系统通知等过程中都不露出内容 |
| F3 | 解锁界面 | 本地按键或移动鼠标时出现解锁界面；支持登录密码或 Touch ID；也能通过 UU 远程输入密码解锁 |
| F4 | 解锁后恢复 | 恢复正常显示和本地输入，隐私屏期间改变的状态全部还原 |
| F5 | 不影响 Computer Use | 隐私屏期间 Computer Use 截图可读、坐标点击和键盘输入有效 |
| F6 | 兼容 UU 远程 | 隐私屏期间 UU 能连接、看到真实画面并正常操作；远程功能不能被隐私屏破坏 |
| F7 | 整夜运行 | 隐私屏期间显示器不睡眠、不触发屏幕保护或系统锁屏，否则 Computer Use 会中断 |
| F8 | 系统锁屏或睡眠时恢复显示 | 监听系统锁屏（`com.apple.screenIsLocked`）和睡眠通知，立即恢复 gamma；否则系统登录界面也是黑的，用户看不到。系统解锁后不自动重新黑屏，需要手动再开 |
| F9 | 兜底恢复 | 任何方式结束进程都会恢复显示；最坏情况长按电源键强制重启，gamma 不会跨重启保留 |
| F10 | 解锁界面超时回黑 | 解锁界面出现后约 20 秒没有本地操作，或认证取消，就关闭解锁界面并重新清零 gamma。原因：解锁界面是普通窗口，会被全屏/Space 过渡移走露出内容，还可能挡住 Computer Use 的点击和键盘输入 |
| F11 | 无响应时先尝试系统锁屏再恢复 | 独立守护检测主线程约 10 秒无心跳后请求系统锁屏，确认最多等待 3 秒，再结束 Curtain；锁屏失败仍恢复显示和输入。正常运行不主动锁系统，正常解锁撤销守护。用户于 2026-11-06 确认实现 |

故障恢复一旦已提交，随后恢复响应的正常解锁/退出必须等待该流程，不能先露出桌面；守护不主动暂停主进程。菜单栏与 CLI 同一用户同时最多一个 gamma 控制者，拒绝的实例不能恢复其他实例的显示曲线。

## 非功能与边界

- 定位为“视觉隐私与日常防误操作”，**不是安全锁屏**。有人在现场可以强制关机、拔电或通过系统级快捷键结束进程；进程意外退出时 gamma 和窗口都会恢复，内容就会露出。产品文案不能称为“锁屏”。
- 不保存密码。认证交给系统 `LocalAuthentication`，不修改系统认证配置。
- 进程崩溃或被结束时应恢复显示，避免把用户锁在黑屏外；安全性优先级排在“能恢复”之后。
- MacBook 需要开盖并接电源；合盖会导致睡眠（外接显示器的合盖模式另行验证）。
- 长期黑屏：本机为 14 寸 MacBook Pro（M4 Pro），屏幕是 mini-LED 液晶，没有 OLED 烧屏问题，用户已接受。gamma 不关闭显示器，背光可能仍在工作，建议开启前把亮度调到最低。自动调亮度要用私有 API，第一版不做。
- gamma 只能整屏显示一种纯色，无法绘制解锁界面；解锁界面必须先盖全屏窗口，再恢复 gamma。

## 关键冲突与对应方案

### 1. 遮挡方式与解锁界面互相矛盾

窗口遮罩在 Space/全屏过渡时会被移走（已实测失败）。gamma 清零能盖住过渡（待验证），但整屏输出都是黑的，**解锁界面也会看不见**。

方案：平时只保持 gamma 清零；检测到本地按键或鼠标后，先显示一个全屏不透明的解锁窗口，再恢复 gamma 并弹出认证。解锁界面出现期间如果正好遇到 Space 过渡，仍可能露出画面，但这时用户本人就在现场，可以接受。认证失败或超时无操作，就关掉解锁窗口并重新清零 gamma。

### 2. 阻止本地操作与 Computer Use、UU 的输入互相冲突（第一版不做）

目前遮罩窗口鼠标穿透，本地人员看不见屏幕，但仍能盲点、盲打。要让“解锁”有意义，必须拦截本地输入，同时放行 Computer Use 和 UU 的输入。

候选做法：用 `CGEventTap` 读取事件来源，硬件键盘和鼠标的事件来源 PID 为 0，合成事件带有发送进程的 PID，据此只拦截硬件事件。需要辅助功能/输入监控权限。

**全部待实测**：
- Computer Use 的点击可能直接投递给目标进程，事件拦截器根本看不到，这样反而不受影响。
- UU 可能通过虚拟 HID 驱动输入，这时会被当作本地硬件事件拦掉。
- 系统级组合键（例如强制退出窗口）能否拦截，还不确定。

### 3. UU 远程

| 方面 | 窗口遮罩 | gamma 清零 |
| --- | --- | --- |
| UU 看到的画面 | 黑色（已实测，`.readOnly`） | 正常桌面（UU 采集的是帧缓冲） |
| 远程看 Codex 在做什么 | 看不到 | 能看到 |
| 判断实体屏幕是否遮住 | 只能作参考 | 完全不能用来判断 |

其他可能的冲突，均待实测：
- UU 自带的“隐私屏/黑屏”功能可能也在改 gamma 或显示配置，断开时把我们的设置恢复，导致露出。这种情况靠 50 毫秒巡检重新清零，但可能闪一下。
- UU 连接时可能调整分辨率或创建虚拟显示器，会触发显示器重新配置，需要对新显示器同样清零。
- UU 的鼠标键盘可能被冲突 2 中的输入拦截挡住。
- 通过 UU 远程解锁：Touch ID 不可用；在系统认证框里输入密码可能受安全输入限制。

### 4. 整夜运行与睡眠、锁屏

显示器睡眠后，系统按“进入睡眠或屏幕保护后要求密码”的设置锁屏，Computer Use 随即失效。隐私屏期间应持有 `IOPMAssertion`，阻止显示器空闲睡眠和屏幕保护；解锁时释放。gamma 清零后背光仍然亮着，整夜会耗电。

## 已决定（2026-11-04，用户确认）

1. **UU 远程看真实画面**，与 gamma 方案一致。UU 自带的隐私屏是否冲突需要实测；如有冲突，用户可以关闭 UU 隐私屏。
2. **必须能通过 UU 远程解锁**，远程功能不能被隐私屏破坏。
3. **第一版不拦截本地输入**：只遮画面，本地人员仍可能盲操作，第一版接受。原 M2 输入边界推迟到后续版本。2026-11-05 更新：用户要求先做一半，拉上时拦截实体键盘鼠标、解锁界面正常使用，并在之后去掉 5 分钟兜底；设计见 [本地输入拦截](subsystems/input-guard.md)。
4. **只用登录密码或 Touch ID 解锁**，不另设紧急恢复办法。进程退出时系统自动恢复显示，本身就是兜底。
5. **接受解锁界面期间约 20 秒的短暂影响**（可能露出内容、Codex 个别操作失败）；超时自动回黑（F10）。（2026-11-05 确认）
6. **解锁后完全恢复正常**：关闭所有窗口、恢复 gamma，应用回到菜单栏待命，不保留任何遮挡或输入影响。

## 第一版设计要点

### 解锁的触发来源

用普通的全局事件监听就会出问题：Computer Use 的合成鼠标、键盘事件也可能被当作“有人回来了”，一触发就恢复 gamma，实体屏幕会露出来。因此：

- 本地触发：只认硬件事件。用只监听、不拦截的 `CGEventTap` 判断事件来源 PID 是否为 0，需要输入监控权限。
- 远程触发：UU 看得到真实画面，可以直接点菜单栏图标里的“解锁”。
- 待实测：Computer Use 的事件会不会被误判为硬件事件；UU 的输入是合成事件还是虚拟 HID。如果 UU 走虚拟 HID，它的鼠标移动也会唤出解锁界面，这可以接受。

### 解锁界面对 Computer Use 的影响（待实测）

解锁界面出现期间 gamma 已恢复，只靠窗口遮挡，所以必须尽快回到黑屏（F10）。为减少对 Codex 的干扰：

- 全屏黑色背景窗口保持鼠标穿透，只有中间的小认证面板接收输入；Codex 的坐标点击只要不落在面板上，就能到达底层应用（窗口遮罩下的穿透点击已实测通过）。
- 认证面板需要键盘焦点，可能抢走 Safari 的焦点。待实测：Codex 键盘输入会不会进入密码框，以及 Codex 激活应用后面板是否失去焦点。
- 在这段时间里，Codex 触发的全屏或 Space 切换仍可能露出内容（窗口方案已实测会闪露），只能靠超时尽快回黑来缩短暴露时间。

### 两条认证路径

| 场景 | 方式 | 说明 |
| --- | --- | --- |
| 本地 | `LAContext.evaluatePolicy(.deviceOwnerAuthentication)` | 系统认证框，Touch ID 加密码回退；系统认证框是否会被解锁窗口挡住需要实测 |
| UU 远程 | 解锁窗口自带密码框，用 OpenDirectory `ODRecord.verifyPassword` 校验当前用户的登录密码 | 公开 API，不保存密码；避免系统认证框的安全输入可能挡住 UU 键盘输入；Touch ID 远程不可用 |

本地也可以使用自带密码框，两条路径在同一个解锁窗口里并存。

### 与 POC 的差异

POC 限制最长 300 秒，是为了实验安全。产品版在隐私屏期间不设时长上限，改由解锁结束；进程退出仍会自动恢复显示。
