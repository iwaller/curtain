# Publishing Curtain updates

Curtain reads stable releases from [iwaller/curtain](https://github.com/iwaller/curtain/releases). The existing user flow is **Check for Updates… → Download and Install → restart**. It is available for ad-hoc builds without an Apple developer membership or notarization. There is no background update schedule or silent installation.

## Preserve the private key

The initial key was generated locally at `artifacts/release-keys/curtain-update.private-key`. This directory is ignored by Git, and private-key files are additionally ignored by suffix. The file has mode `0600` and its containing directory `0700`. It contains a randomly generated 32-byte Ed25519 private key (44 Base64 characters, approximately 128-bit security); it is not encrypted. File permissions do not protect it from other programs running as the same user. Back up this file privately outside the checkout before deleting `artifacts/`, moving machines, or cleaning ignored files. Do not upload the key, paste it into release notes, commit it, or attach it to a release.

For routine maintenance, keep the local file for packaging and store its complete contents as a secure note or protected attachment in a password manager. Record the repository and original filename alongside it. Restore the same contents on a new computer and run `chmod 600 /path/to/curtain-update.private-key` before signing. Use the same key for each release; it has no scheduled expiry. Keep an encrypted backup of the password-manager vault or use an encrypted storage volume if that is your established backup method.

Only `Resources/UpdatePublicKey.txt` is committed. The build compiles this public key into the app and records it in the signed Info.plist. Ordinary builds do not access the private key. Keep the same key for future versions: losing it prevents authenticated updates to existing installations. Key rotation currently requires users to install a new version manually.

For a new fork with no existing users, generate a new key pair with new output paths:

```bash
./scripts/update-signing.sh generate artifacts/my-fork/curtain.private-key artifacts/my-fork/public.txt
```

Copy that public file to `Resources/UpdatePublicKey.txt` before the fork's first build. Generation refuses to overwrite existing outputs. Never replace the current project's public key just to fix a missing private key.

## Build and sign

Releases support Apple Silicon (arm64) only. Use a native terminal on an Apple Silicon Mac; the build rejects Intel/Rosetta hosts and explicitly targets arm64. The DMG packager also rejects app/helper binaries that are not arm64-only. `Curtain-arm64.dmg` identifies the installer architecture; updater attachment names stay `Curtain.zip` and `Curtain.zip.sig`.

1. Update `CFBundleShortVersionString` in `Resources/Info.plist` to a higher numeric version, for example `0.2.0`. Use a matching release tag, such as `v0.2.0`.
2. Run the release packager, using the backed-up private key's location if it has moved:

   ```bash
   ./scripts/package-release.sh artifacts/release-keys/curtain-update.private-key
   ```

   The script defaults to ad-hoc code signing for both the app and watchdog, builds `build/Curtain.zip`, creates `build/Curtain.zip.sig`, and packages `build/Curtain-arm64.dmg`. The compressed, read-only DMG contains the same signed app and an Applications shortcut for initial installation; the ZIP remains the in-app update format. Set `CURTAIN_SIGN_IDENTITY` explicitly to use a local certificate instead. The signing tool refuses a key that does not match the public key embedded in the archive. Every successful rebuild deletes the old `.sig` and DMG; sign the final ZIP after its last modification.

3. Create a stable GitHub Release with the matching tag and attach **all three** files, named exactly `Curtain-arm64.dmg`, `Curtain.zip` and `Curtain.zip.sig`. Point users to the DMG for first installation; the updater downloads the ZIP and its signature. Do not rename or recompress the signed ZIP. Drafts and prereleases are ignored.

To regenerate only the DMG from an already built app, run `./scripts/package-dmg.sh`. This does not modify the update ZIP or its signature. The image is created from an explicit staging directory containing only `Curtain.app` and the Applications link; the source checkout and private key are never added.

The `.sig` file is Base64 text containing a 64-byte Ed25519 signature over the entire ZIP, including the app, helper, version and embedded public key. It is public and should accompany the download. Source archives generated by GitHub are not update packages.

## Verification and installation limits

Run `python3 scripts/test-updates.py` and `python3 scripts/test-localizations.py` after building. Tests use separate temporary signing keys and isolated application fixtures, never the production private key or live installed app. Signing tests cover valid ad-hoc updates, incorrect keys, archive tampering, malformed signatures, missing helpers, version/key mismatch, unsafe archives, privacy-session refusal, cancellation and rollback.

The updater authenticates the downloaded archive before parsing it, checks bundle and nested code integrity, and keeps all existing privacy-session and atomic replacement protections. A failed signature never falls back to trusting the server or an Apple certificate. An initial version that predates this trust root must be installed manually once.

Gatekeeper approval and Accessibility permission are separate from update authenticity. Opening the DMG and copying its app does not remove macOS trust checks. First launch of a downloaded, unnotarized app can require **System Settings → Privacy & Security → Open Anyway**. Updating an ad-hoc build may require Accessibility authorization again. Actual GitHub download/install/restart and cross-Mac authorization retention remain unverified until a real release is published and tested.
