# 本地输入拦截

状态：2026-11-06 本地唤出、键盘拦截、Touch ID、20 秒回黑和 Ctrl+Cmd+Q 现场通过；开启拦截后的 Codex/UU 完整回归待测。[心跳守护与故障锁屏](recovery-watchdog.md)已实现，替代菜单栏应用默认 5 分钟兜底；验收见[验证记录](../verification.md)。closed 时拦截实体输入，unlocking 时放行。

## 目标

| 状态 | 实体键盘/鼠标/触控板 | Codex、UU 等模拟输入 |
| --- | --- | --- |
| open | 不处理 | 不处理 |
| closed | **全部吞掉**，只把“有人动了”作为唤出解锁界面的信号；少数系统级恢复键放行 | 放行 |
| unlocking | 全部放行（解锁界面、Touch ID 系统框正常使用；20 秒无操作回黑） | 放行 |

吞掉唤醒事件本身：第一下点击或按键不会落到下面看不见的应用里。

## 识别实体输入

主动（可修改）`CGEventTap`，位置 `kCGSessionEventTap`、`headInsert`。判断条件同时满足才算实体输入：

- `eventSourceUnixProcessID == 0`：HID 系统产生，没有发送进程；
- `eventSourceStateID == kCGEventSourceStateHIDSystemState (1)`：作为第二道确认（待实验确认实体事件确实是 1，模拟事件不是）。

已知事实与待验证：

- UU 的鼠标事件来源 PID 为 UURemoteServer（实测 5182），不会被当成实体输入。UU 键盘尚未在全局监听中出现过（缺权限），需实验。
- Codex 的点击从未出现在全局事件监听里，推测直接投递给目标进程，不经过会话层；即使经过，PID 也不为 0。需实验确认 tap 看不到或放行。
- **本机装有 Karabiner-Elements**：它独占实体键盘，再通过自己的 DriverKit 虚拟 HID 键盘重新发出按键。这类事件从 HID 层进入系统，预计 PID 仍为 0、视为实体输入，这正是想要的；需实验确认。若 Karabiner 也接管了鼠标/触控板，同理。
- 风险：将来若某个远程或自动化工具改用虚拟 HID 设备输入，它会被当成实体输入而被拦。届时需要按设备区分，`CGEventTap` 拿不到设备信息，要改用 IOHIDManager，不在本期范围。

## closed 状态的拦截范围

| 事件 | 处理 |
| --- | --- |
| keyDown / keyUp / flagsChanged | 吞掉；第一个触发唤醒 |
| 鼠标移动、按下/抬起、拖动、滚轮 | 吞掉；第一个触发唤醒（现有逻辑：移动即唤醒） |
| 系统定义键（音量、媒体，type 14） | 吞掉，不唤醒（需实验确认 tap 能看到） |
| 触控板手势（切 Space、调度中心） | 尽量吞掉；能否在会话层拦住待实验 |
| **Ctrl+Cmd+Q** | 实测会话层 tap 能看到并能拦住，必须显式放行。系统锁屏后 `SessionWatcher` 强制拉开，锁屏本身要求登录密码，不降低安全性 |
| 拉上前已按下的键的 keyUp | 放行，避免修饰键卡住 |

拦不住、也不打算拦：电源键、合盖（触发睡眠 → 强制拉开）、Touch ID 传感器（不经过事件系统）。

## 失败语义：宁可放开

0. **系统锁屏时绝不拦截。** 实测锁屏界面的密码输入也经过会话层 tap。收到 `com.apple.screenIsLocked` 立即停用 tap（随强制拉开一起）；回调里再查一次会话字典 `CGSSessionScreenIsLocked`，锁屏期间一律放行，作为第二道保险。

1. **tap 放在主线程 run loop。** 主线程卡住时回调超时，系统自动禁用 tap（`tapDisabledByTimeout`），输入恢复。不放到独立线程，否则主线程卡死、界面不响应时仍在拦截，人会被挡在外面。
2. 收到 `tapDisabledByTimeout` / `tapDisabledByUserInput`：主线程正常时重新启用并记日志；连续多次被禁用则放弃拦截，菜单显示警告。
3. **进程退出（崩溃、被结束）**：tap 随进程消失，gamma 由系统恢复。
4. **缺少辅助功能权限**：tap 创建失败时仍可拉上（只遮画面），菜单显示“未拦截键盘鼠标（缺少辅助功能权限）”，日志记录。
5. **安全输入**：其他应用开启安全键盘输入（终端的 Secure Keyboard Entry、密码管理器等）时，tap 看不到键盘事件，按键会穿透。只记录为已知限制。

## 去掉 5 分钟兜底后的恢复路径

| 故障 | 恢复办法 |
| --- | --- |
| 正常 | 动鼠标或按键 → 解锁界面（不拦截）→ Touch ID 或密码 |
| 解锁界面有 bug（如今天的面板被背景挡住） | Ctrl+Cmd+Q → 系统锁屏 → 强制拉开；登录密码进入 |
| 主线程卡死 | tap 被系统禁用，输入恢复；但 gamma 仍是黑的，所以需要下面的守护进程 |
| 守护进程 | 拉上前启动独立子进程，主线程每秒发心跳；约 10 秒收不到时先暂停 Curtain、请求并确认系统锁屏（最多 3 秒），再强制结束 Curtain；失败时仍恢复显示/输入。正常解锁先撤销守护，不锁系统。完整契约见[心跳守护](recovery-watchdog.md) |
| 远程 | UU 菜单“解锁…”+ 密码；或 UU 发 Ctrl+Cmd+Q；或 SSH `kill -TERM` |
| 最坏 | 长按电源键重启，gamma 与 tap 都不跨重启保留 |

长期无人值守前，上表恢复路径需现场验收（守护进程用 `kill -STOP` 模拟卡死）；进程级模拟与真实系统锁屏分别记录。

## 权限与签名

- 主动 tap 需要“辅助功能”权限。有了权限，键盘也能唤出解锁界面（现在只认鼠标）。
- ad-hoc 签名每次编译都会变，系统会把权限当成新应用而失效。需要先在钥匙串创建一个自签名代码签名证书（如 “Curtain Dev”），`build.sh` 改用它签名，并把应用安装到 `/Applications/Curtain.app`，权限才能在重新编译后保留。

## 现场识别实验（实现前）

用一个只监听的探针（`build/` 下，需辅助功能/输入监控权限）记录每类事件的 `pid / stateID / keyboardType`：

1. 实体键盘（经 Karabiner）按键、修饰键、Ctrl+Cmd+Q；
2. 触控板移动、点击、滚动、三指/四指手势；音量/亮度键；
3. Codex 点击和键入；
4. UU 鼠标和键盘（远程即可）。

通过标准：1、2 全部 `pid=0, stateID=1`；3、4 全部不满足。任何一项不符，先调整识别条件再实现。

## 实现说明（2026-11-06）

- `InputGuard.setMode(.block)` 在拉上时创建 tap；创建失败（无辅助功能权限）时退回原全局鼠标监听，只遮画面，菜单显示警告。
- 唤醒：closed 下第一个被吞掉的实体事件异步通知控制器，进入解锁界面；背景画好、gamma 恢复后（`ready`）才切到 `.observe`，此前的点击仍被吞掉。
- Ctrl、Cmd 单独按下或组合（不含其他修饰键）的 flagsChanged 放行且不唤醒，Ctrl+Cmd+Q 的 keyDown 放行；其他修饰键会唤醒。
- 所有抬起事件（keyUp、mouseUp）放行，避免卡键。
- 回黑（20 秒、取消、Esc）时先清零 gamma，再切回 `.block`。
- 解锁界面期间 tap 也看得到点在 Curtain 控件上的点击；只有控件以外的实体点击才重新发起 Touch ID。
- 被系统禁用（超时/用户输入）时重新启用；60 秒内超过 5 次则放弃拦截（放行），记日志。
